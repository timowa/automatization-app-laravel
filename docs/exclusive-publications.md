# Эксклюзивные публикации

## Входящие данные

`offers[].exclusive` — необязательное JSON boolean (`true` / `false`). Отсутствие означает `false`; строки, числа и `null` отклоняются. Вариант `exclisuve` не является поддерживаемым полем.

Признак хранится в снимке `offers`. Идентификатор объекта — `offers.code`, город — существующее поле `offers.city`.

Приём запроса сериализован блокировкой по коду объекта. Дедупликация сравнивает последний принятый снимок (без сохранённого исходного `payload` ошибки/дубля) по коду, цене, этапу, статусу, агенту и эксклюзивности. Это сохраняет переходы `false → true → false`, в том числе возврат к ранее встречавшимся значениям. Сохранённые дубли не меняют принятое состояние объекта.

## Два основания запуска

1. **Завершение основной публикации.** Все задачи должны быть `success` или `failed`. При ошибке родителя ожидающие потомки рекурсивно становятся `failed`. Незавершённая задача задерживает запуск. Ограничение 24 часов для этого основания не применяется.
2. **Переход существующего объекта `false → true`.** Основной сценарий не выполняется, даже при одновременном изменении других полей. Используется последний основной сценарий по тому же коду из снимков, предшествующих текущему. Отдельный запуск разрешён, только если за предшествующие 24 часа нет любого запуска эксклюзива по этому коду. Ровно 24 часа — разрешено.

Первый эксклюзивный снимок проходит обычный сценарий. В обоих случаях требуется шаблон основного сценария. Если последняя основная публикация отсутствует или не имеет шаблона, дополнительные действия не создаются. Более старый подходящий сценарий не ищется. При переходе берутся актуальные характеристики нового снимка и шаблон исторической основной публикации.

Правила реализуют `ExclusiveRule::rejection()`: `null` означает разрешение, строка — причину штатного пропуска. Список расширяется в `ExclusivePublicationService::rules()`.

## Получатели и контент

Получатели — уникальные существующие агенты, для которых есть хотя бы одна запись `offers` с совпадающим `city`. Успех старых публикаций, их наличие и `skip_reason` не учитываются. Исходный агент исключён. Отсутствие доступа к ВК не исключает получателя, а отражается ошибкой его задач.

Список фиксируется при регистрации запуска и не изменяется при повторе. Отсутствие получателей — успешная регистрация пустого запуска, учитываемая ограничением 24 часов.

Дополнительная публикация имеет `scenario=exclusive`, исходный `offer_id`, своего `agent_id` и `exclusive_run_id`. Запуск хранит исходный сценарий, используемый для выбора существующего шаблона. Новые офферы для получателей не создаются.

Цепочка: `VK_UPLOAD_IMAGES → VK_POST → VK_STORY`. История однократная. Репосты, товары, комментарии и периодические истории не создаются. Контакты, доступ к ВК и страница принадлежат получателю. История ссылается на его пост.

Для дополнительных публикаций загрузки фотографий хранятся в `offer_image_uploads` отдельно по изображению и агенту с явным владельцем фотографии. Основные публикации сохраняют совместимость с `offer_images.media_id`.

## Надёжность и повтор

`exclusive_object_locks` сериализует регистрацию запусков и проверку интервала по коду. `trigger_key` защищает от повторного запуска одной основной публикации/одного перехода. Уникальность `(exclusive_run_id, agent_id)` защищает получателей от дублей.

`PublicationCompletionService` проверяет итог задач и регистрирует запуск атомарно. Изменения конечных состояний планируют `CheckPublicationCompletionJob`. Сбой планирования не отменяет результат выполненной задачи.

Команда `publications:recover-exclusive` каждую минуту:

- проверяет ещё не обработанные основные публикации эксклюзивов;
- восстанавливает сохранённые переходы, для которых нет результата;
- разворачивает зарегистрированные, но ещё не обработанные запуски;
- отправляет ожидающие дополнительные задачи;
- возвращает в отправку задачи, которые более 15 минут остались `queued`;
- восстанавливает итоговые состояния запусков.

Восстановление выполняется только через существующие записи. Задания загрузки, поста и истории имеют взаимное исключение по задаче. Сохранённый пост используется повторно; для `wall.post` передаётся стабильный `guid` задачи.

Перед дополнительной историей и при повторной попытке её отправки проверяются доступные истории получателя по ссылке на пост. Идентификатор результата сохраняется. ВК не предоставляет бессрочный ключ идемпотентности истории: если результат прежней попытки неизвестен более суток, задача остаётся ошибочной и требует ручной проверки вместо повторной публикации вслепую. `external_started_at` фиксирует первую попытку отправки.

Повтор восстанавливает неуспешные задачи с учётом зависимостей; успешные не повторяются. Новый запуск и новое время ограничения не создаются. Команда `publication:task-repeat` для неуспешной задачи восстанавливает неуспешные задачи её публикации, чтобы зависимые действия не оставались заблокированными.

Исходящие запросы к `api.vk.com` проходят общий ограничитель: интервал не менее 350 мс между началами запросов. Все воркеры должны использовать общий cache store, поддерживающий атомарные блокировки.

## Админка

Список офферов сохраняет одну строку на снимок. Добавлены фильтр и бейдж эксклюзивности, отдельное состояние дополнительных публикаций. Основная связь `Offer::publication()` и правила сценариев исключают дополнительные публикации.

На `/offers/{offer}/exclusive` отображаются основной результат, причина запуска/пропуска, шаблон, время, прогресс, получатели, их задачи и ссылки на результаты. Во время ожидания страница обновляется каждые 10 секунд. Повтор доступен для всех дополнительных публикаций или одного получателя. Основные ошибки повторяются прежней кнопкой списка.

Статистика привязана к агенту публикации, дополнительные результаты представлены сценарием «Эксклюзив». Периодические истории выбирают только основной пост.

## Выпуск

1. Установить зависимости (`composer install`; на production допустим `--no-dev`). Pest добавлен только в dev-зависимости.
2. На время обновления остановить обработку очереди, чтобы старые воркеры не выполняли новые задачи.
3. Выполнить `php artisan migrate --force`: миграция добавляет поля и таблицы, заполняет агентов существующих публикаций.
4. Перезапустить воркеры и убедиться, что стандартный Laravel scheduler работает. Отдельный cron для новой команды не требуется.
5. Использовать общий cache store для всех воркеров. При нескольких серверах локальный файловый cache не обеспечивает общий лимит.

Миграция не запускает публикации старых офферов: существующие записи получают `exclusive=false`.

Проверки: `php vendor/bin/pest tests/Feature/ExclusivePublicationTest.php`. Тесты используют SQLite и подмену ВК, реальные публикации не выполняются.
